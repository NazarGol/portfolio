01EngineeringTrapAggressor / StateWatch

Sanctions Checker — EU · US · UK export-control lookup

A local tool that answers "is this product under sanctions?" — built so the LLM structurally cannot invent an answer.

Problem

An investigator tracking sanctions evasion has a product description in Ukrainian, or an HS code off a customs declaration, and needs to know whether it is restricted, under which instrument, since when, and where the official text says so. By hand that means reading three legal regimes — 13 EU annexes, 3 US BIS supplements, 11 UK schedules — each with its own code format and amendment history.

Built

A FastAPI service over a 7,676-entry SQLite database, with 15 EU annex parsers, UK schedule parsers and US BIS supplement parsers that rebuild the database from official sources. Product names are accepted in Ukrainian and English; every answer returns its legal basis, annex, restriction type, date enacted and a deep link into the source document.

Classification runs four tiers: an alias table of ~200 known products, then an LLM stage, then keyword-intersection SQL with progressive relaxation, then a rapidfuzz fallback.

The design decision worth explaining is tier two. The naive approach — asking a model for an HS code — fails in the worst possible way: it returns a plausible, correctly-formatted code that does not exist. In a compliance context that is a false clearance. So the model is never asked for a code. It is asked only for the 2-digit HS chapter, a coarse classification into 97 buckets that language models do reliably. Every database row in that chapter is then fetched, and the model re-ranks within that list. Its output is a selection from real rows, not a generated string — so a code that is not in the database cannot come out of the pipeline. A wrong chapter yields a wrong but checkable answer pointing at a real entry. It is never wrong by inventing one.

Stack
Python 3.10+FastAPISQLite → PostgreSQL pathOllama qwen2.5:7brapidfuzzpyhscodesDocker Composenginx + certbotpytest
Result

96.8% classifier accuracy on a 125-query bilingual (UK/EN) test set. 7,676 active sanctions entries across three jurisdictions — EU 2,332 · US 2,797 · UK 2,547. ~7,300 lines of Python, 64 tests across 8 test modules.

02AnalysisIndependent research

The UK has designated none of them

A four-jurisdiction coverage gap across 97 Russian military-AI entities.

Problem

Sanctions policy has tracked hardware — components, microelectronics, supply chains — because goods are legible to a goods-based regime. The developer layer writing the targeting, recognition, monitoring and censorship software has been tracked much less. I wanted to know how much less, and where exactly the holes are.

Built

I mapped 97 Russian companies, institutes and state structures developing AI for military, surveillance and information-control applications, and checked each against four sanctions regimes. Every entity carries registry number (OGRN), tax number (INN), addresses in Russian, Ukrainian and English, a sourced designation justification, and an explicit listed/not-listed status per jurisdiction.

Recording OGRN and INN rather than names is the load-bearing choice: Russian corporate names are unstable and routinely re-registered, but a registration number survives renaming and is what makes an entity matchable against a sanctions list or a procurement record.

Cluster III is the counter-disinformation cut. Fifteen entities building media monitoring, censorship and cyber-operations tooling — the systems that detect, characterise and act on the information environment. US coverage is comparatively strong here at 7 of 15, its best ratio of any cluster. The UK's is zero. Several are marketed openly to government buyers, and at least one claims publicly to forecast public reaction to state initiatives and to identify and "work with" difficult authors and opinion leaders. That is the point at which media monitoring stops being analytics.

Result

62% of the 97 carry no Western designation at all. 41% carry none in any of the four jurisdictions. 20 are Ukraine-listed with no Western follow-through — already assessed by the state fighting the war, with the evidentiary work done and published, and untouched by any Western regime.

03Analysis · CodeFIMI / coordinated behaviour

Pro-Russian information network in Moldova

Graph analysis of 27 Telegram channels — is the structure organic, or coordinated?

Problem

Within a fixed perimeter of 28 Telegram channels pushing pro-Russian and anti-Western content in Moldova, does the observable structure look organic — or does it show coordination? The channel set was defined in advance, so this describes structure inside a boundary rather than a network discovered from scratch. That limitation is stated in the report rather than buried.

Built

A batch collection script driving GroupInt across all 28 targets — 500 messages each, endorsement extraction, flood-wait handling, failures logged and skipped rather than aborting — into a Neo4j graph. Nodes: channels, messages, users. Edges: ENDORSES, extracted from @username and t.me/ links in message text. Degree metrics in Cypher; the GDS plugin was unavailable, so clustering is an analyst's reading rather than an algorithm's, and the report says so.

Structural finding. @primulinmd is the single node receiving endorsements from all three narrative pipelines — in-degree 83, out-degree 8. A channel cited by ideologically distinct clusters that cites almost nobody is the network's shared authority. KP Moldova is the distribution hub at out-degree 129, in-degree 0: it pushes, it does not receive.

Coordination indicators, each weighted differently rather than collapsed into one claim: byte-identical texts published same-day by @e_tiraspol and @pridnestrovec; four or more channels framing the 27 May gas VAT decision within hours in near-identical wording; and a narrow shared set of externally cited channels across otherwise unconnected clusters.

Stack
Python 3.13Neo4j 5.xCypherTelethon (via GroupInt)Docker
Result

27 channels indexed of 28 targeted · 23,110 messages · 424 endorsement links across 164 unique channel pairs · 4 clusters mapped.

04MethodologyLLM output reliability

Measuring LLM fabrication rate in OSINT profiling

How much of a model's output is invented — and does prompt construction change that, or only the tone?

Problem

Analysts use language models to profile people. The failure mode everyone names is hallucination; the failure mode that actually reaches finished reports is subtler. I wanted a number rather than an intuition.

Built

The same profiling task run twice — same model, same subject, search explicitly disabled on both sides — varying only prompt construction. Twelve discrete claims extracted from the output and checked one at a time against public sources, each scored true / hallucinated / unverifiable / partial, with the basis recorded per claim.

The dangerous errors are the ones that look right. The model placed the subject at the wrong university — and the university it named is a real institution in the same city. Locally plausible, superficially correct, invisible without a deliberate check. A hallucination that looks wrong gets caught in review; one that looks right becomes a sourced claim.

The 33% unverifiable bucket is arguably worse than the 17% fabricated. Claims like "speaks at conferences" and "part of a new wave of managers" cannot be disproven — so they pass review as harmless colour, and they were generated from nothing. I score them as their own category, because collapsing them in either direction is how unsourced claims enter analysis.

What moved fabrication to zero was not the persona or the tone instruction. It was two clauses — use only facts explicitly present in the text, and if a field is absent, return null — which change the model's implicit objective from producing a complete-looking profile to reporting what the source supports.

A prompt-injection test is documented alongside: a hostile instruction embedded in a source document was detected and refused unprompted. The correct conclusion is narrower than "models are safe" — one passing test on one model is not a control.

Result

Unconstrained prompt: 17% explicit hallucination, 33% unverifiable claims. Source-constrained prompt on the identical task: 0% fabrication.

Links
github.com/NazarGol/llm-verification-osint

My first attempt at this comparison was invalid — I had compared a tool with retrieval against one without, not two prompts. The repo documents that error and the fix, because catching a confounded comparison before publishing is the same skill as catching a plausible hallucination before it ships. The verification subject is anonymised and identifying links removed.

05CodeAgent reliability

Querying 77k sanctions entities — SQL and an agent

A local analytics stack over the consolidated sanctions corpus, and what the agent got wrong.

Problem

Can a local stack put the full consolidated sanctions corpus behind plain SQL and a natural-language agent — and can the agent's answers be trusted without checking its work?

Built

A Dockerised MindsDB instance over the OpenSanctions consolidated dataset, with two query paths deliberately compared: a manual-context model where I pull data with SQL and hand it over as text, and a tool-calling agent that writes its own SQL. Local models could not do tool calling reliably, so that path runs on Groq while the manual path runs on local Ollama.

The finding is a negative one and it is the useful part. Asked how many sanctioned entities are from Russia, the agent returned 21,210. My own direct SQL returned 19,238. Neither is wrong — the gap is almost certainly multi-country records like ru;ua — but that is a reconstruction after the fact. The agent did not show its query, so there was no way to tell which question it had answered without redoing the work it was meant to save. For sanctions screening that is disqualifying on its own terms: a number without its query is an assertion, not a finding.

A second observation from the same session: the second-largest country group in the dataset is NULL. For anyone filtering on jurisdiction, that is a silent hole in coverage rather than an empty category.

Stack
MindsDBDockerOllama gemma3:4bGroq APISQLOpenSanctions
Result

76,996 sanctions entities queryable in SQL, with both a manual-context path and a tool-calling agent — and a documented auditability failure in the agent path.

06CodeCollection pipeline

Corpus Editor — Telegram video pipeline

Bulk collection → feature extraction → embeddings → a navigable 3-D field.

Problem

A few hundred short videos scraped from Telegram are too many to watch and too unstructured to grep. Filenames tell you nothing about what is in the footage, or which clips resemble each other.

Built

A pipeline that collects videos from public Telegram channels via Telethon, reduces each to a feature vector — ffprobe metadata, librosa audio energy, OpenCV optical-flow motion and edge complexity, MediaPipe face counts, CLIP zero-shot scene labels, k-means dominant colours, and a CLIP ViT-B/32 embedding — then projects all embeddings through UMAP into 3-D and computes top-10 cosine nearest-neighbour edges. SQLite behind a FastAPI service feeding a Three.js frontend.

Both stages are resumable: downloaded files are skipped on re-scrape, embedded nodes on re-process. At corpus scale a failure 80% through a run should cost 20%, not everything.

This started as a tool for a film project, not an intelligence one. It is here because the pipeline underneath — bulk Telegram collection, per-item feature extraction, embedding, dimensionality reduction, an API over the result — is what a media-monitoring system needs, and I would rather show one I built end to end.

Stack
Python 3.11+TelethonFastAPISQLiteCLIP ViT-B/32UMAPOpenCVMediaPipelibrosaffmpegThree.js
Result

153 videos from 12 channels with 1,100 similarity edges, from a target list of 102 Ukrainian public channels.

Links
github.com/NazarGol/corpus-editor

No credentials, no Telegram session file and no scraped corpus are published — the pipeline is the contribution.

08ResearchAdversary capability

Russia Context Platform

Frame

Adversary-capability research: modelling how synthetic local personas could be constructed from open sources, in order to understand what detection would have to catch.

Why

Everything above this entry is detection-side work — mapping networks, measuring model reliability, checking claims against sources. This is the same problem approached from the other direction. A detection system is only as good as its model of what it is trying to detect, and that model has to come from somewhere.

Status

Unfinished, and not open-sourced. Case study text only — no repository, no code, no screenshots. I am happy to discuss the research questions and what they imply for detection design; I do not publish the capability.
