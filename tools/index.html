Sanctions Checker — EU · US · UK export-control lookup

Tool 2026 · TrapAggressor / StateWatch Repository →

Answers one question — is this product under sanctions? — and returns the legal basis, annex, restriction type, date enacted and a deep link into the official source document.

An investigator tracking sanctions evasion has a product description in Ukrainian, or an HS code off a customs declaration. Answering by hand means reading three legal regimes: 13 EU annexes, 3 US BIS supplements, 11 UK schedules, each with its own code format and amendment history.

Classification runs four tiers — an alias table of roughly 200 known products, then an LLM stage, then keyword-intersection SQL with progressive relaxation, then a rapidfuzz fallback. The tier worth explaining is the second.

The answer is picked, not written

Asking a model for an HS code fails in the worst available way. It returns a plausible, correctly-formatted code that does not exist — and in a compliance context, a confident wrong code is a false clearance. The failure is not that the model is unreliable; it is that a generated string has no source to check it against.

So the model is never asked to produce a code. It is asked for the two-digit HS chapter — a coarse classification into 97 buckets, which language models do well. Every database row in that chapter is then retrieved, and the model chooses one. Its output is a selection from rows that already exist, which means a code absent from the database cannot leave the pipeline. A wrong chapter produces a wrong but checkable real entry, never an invented one.

96.8% classifier accuracy on a 125-query Ukrainian-and-English test set. 7,676 active sanctions entries across three jurisdictions — EU 2,332 · US 2,797 · UK 2,547. ~7,300 lines of Python; 64 pytest tests across 3 modules, plus 5 accuracy harnesses that are how the 96.8% was measured.

Corpus Editor — Telegram video pipeline

Tool 2026 Repository →

A few hundred short videos scraped from Telegram are too many to watch and too unstructured to grep. This turns them into a corpus you can traverse.

Videos are collected from public channels, each reduced to a feature vector, the vectors projected into three dimensions, and nearest-neighbour edges computed so visually similar material sits together and can be navigated rather than searched.

Per-video extraction covers ffprobe metadata, librosa audio energy, OpenCV optical-flow motion and edge complexity, MediaPipe face counts, CLIP zero-shot scene labels and k-means dominant colours, alongside the CLIP ViT-B/32 embedding itself.

This began as a tool for a film project, not an intelligence one. It is here because the pipeline underneath — bulk Telegram collection, per-item feature extraction, embedding, dimensionality reduction, an API over the result — is the same pipeline a media-monitoring system needs, and I would rather show one I built end to end.

No credentials, no Telegram session file and no scraped corpus — the pipeline is the contribution

Querying 77k sanctions entities — SQL and an agent

Tool 2026 Repository →

A local analytics stack over the consolidated sanctions corpus — and a negative finding about the agent that turned out to be the useful part.

A Dockerised MindsDB instance over the OpenSanctions consolidated dataset, 76,996 entities, with two query paths deliberately compared. One is a manual-context model: I pull data with SQL and hand the result over as text. The other is a tool-calling agent that writes its own SQL. Local models could not do tool calling reliably, so that path runs on Groq while the manual path runs on local Ollama.

Asked how many sanctioned entities are from Russia, the agent returned 21,210. My own direct SQL returned 19,238. Neither is wrong — the difference is almost certainly multi-country records like ru;ua — but that is a reconstruction after the fact. The agent did not show its query, so there was no way to establish which question it had answered without redoing the work it was supposed to save.

For sanctions screening that is disqualifying on its own terms. A number without its query is an assertion, not a finding. The correct design is that the agent surfaces generated SQL alongside every answer, and the answer is treated as a draft until that SQL has been read.

A second observation from the same session: the second-largest country group in the dataset is NULL — entities with no jurisdiction recorded. For anyone filtering on country, that is a silent hole in coverage rather than an empty category.

Measuring LLM fabrication rate in OSINT profiling

Method 2026 Repository →

When an analyst uses a language model to profile a person, how much of the output is invented — and does prompt construction change that number, or only the tone?

The same profiling task, run twice. Same model, same subject, search explicitly disabled on both sides so the only variable is prompt construction. Twelve discrete claims extracted from the output and checked one at a time against public sources, each scored true, hallucinated, unverifiable or partial, with the basis recorded per claim.

The dangerous errors are the ones that look right. The model placed the subject at the wrong university — and the university it named is a real institution in the same city. Locally plausible, superficially correct, and invisible without a deliberate check. A hallucination that looks wrong gets caught in review; one that looks right becomes a sourced claim in someone's report.

The 33% unverifiable band is arguably worse than the 17% fabricated. Claims like "speaks at conferences" or "part of a new wave of managers" are not falsifiable, so they survive review as harmless colour — having been generated from nothing.

What moved fabrication to zero was not the persona framing or the tone instruction. It was two clauses — use only facts explicitly present in the text and if a field is absent, return null — which change the model's implicit objective from producing a complete-looking profile to reporting what the source supports.

Prompt injection

A hostile instruction embedded in a source document was detected and refused unprompted, and flagged explicitly as a manipulation attempt. The correct conclusion is narrower than "models are safe": the injection was well-formed and was caught by this model on this day with no system-level defence in place. One passing test is not a control.

My first attempt at this comparison was invalid — I had compared a tool with retrieval against one without, not two prompts. The repository documents that error and the fix, because catching a confounded comparison before publishing is the same skill as catching a plausible hallucination before it ships.

Scope and limits

Sample
One subject, twelve claims. An order-of-magnitude signal about a failure mode, not a benchmark — the method transfers, the exact numbers do not
Subject
Anonymised: a serving regional official in Ukraine. Identifying source URLs removed; source types named so the method stays reproducible
Scoring
"Unverified" means no public source was located either way — kept as its own category rather than folded into true or false
Reproduction
Model versions were not pinned at the time of the run

Russia Context Platform

Research 2026

Adversary-capability research: modelling how synthetic local personas could be constructed from open sources, in order to understand what detection would have to catch.

Everything else in this portfolio is detection-side work — mapping networks, measuring model reliability, checking claims against sources. Detection carries a dependency that is rarely stated: a detector is only as good as its model of what it is trying to catch, and that model has to come from somewhere. If the only available description of a synthetic persona is "an account that seems fake", the detection surface is intuition.

So I approached it from the other side. Rather than asking what a fake account looks like, I asked what a convincing one would have to know — and treated each requirement as a place a detector can look.

Each class is cheap to approximate and expensive to sustain, and each fails in a characteristic way. That asymmetry is the useful part — detection does not have to prove an account is synthetic, only to find the class where the approximation gives way.

Framed this way the work is a detection specification rather than a capability. It says where to look and in what order: start with the class cheapest for a defender to test and most expensive for an adversary to sustain, and treat coherence across classes, rather than any single anomaly, as the signal. It also sets a realistic ceiling. Several of these classes are approximable well enough to survive casual review, which is an argument for building detection that assumes competent synthesis rather than sloppy synthesis.

Unfinished, and not open-sourced. Case study text only — no repository, no code, no screenshots, and nothing here describes how such a persona would be constructed. I am glad to discuss the detection reasoning and what it implies for tooling; I do not publish the capability.
